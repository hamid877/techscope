## 1. Executive Summary

TechScope is a lookup tool. A developer enters the name of an npm or PyPI package, and TechScope returns a deterministic, 0–100 Health Score computed from six objective ecosystem signals — commit activity, release behavior, issue handling, contributor concentration, download trend, and documentation presence — sourced from GitHub, npm, and PyPI. Every score ships with a per-metric breakdown, a completeness indicator, and any known data-quality caveats (provisional, lower-confidence, insufficient-data). A short natural-language explanation, generated by an LLM that reads the already-computed score and cannot alter it, translates the numbers into plain English.

There is no login, no personalization, no chat interface, and no feature whose value depends on the platform knowing who the user is. V1 answers exactly one question, for exactly one package at a time: *based on objective ecosystem signals, is this technology healthy and worth adopting?*

## 2. Vision Statement

Developers currently answer "is this technology healthy?" by manually cross-referencing GitHub activity, download counts, issue trackers, and secondhand opinions from blogs and forums — a process that is slow, inconsistent between people, and easy to get wrong on gut feel alone. TechScope replaces that manual cross-referencing with a single deterministic score, computed the same way every time, with the full calculation shown to the user rather than hidden behind a black box. The long-term vision (Section 19) is a broader, cohort-aware version of this same score across more ecosystems. The V1 vision is narrower and non-negotiable: prove the six-metric model on npm and PyPI against a curated, validated benchmark, and prove that AI can explain a score without ever being allowed to influence it.

## 3. Problem Statement

Evaluating whether a programming language, framework, library, or developer tool is healthy and worth adopting currently requires visiting multiple disconnected sources — the GitHub repository, the npm or PyPI page, release notes, documentation, and informal community sentiment on blogs or Reddit — and manually synthesizing an opinion. This process:

- Takes real, non-trivial time per technology evaluated.
- Produces inconsistent conclusions depending on which sources a given developer happens to check.
- Is vulnerable to hype, recency bias, and marketing rather than objective maintenance signals.
- Has no standard, repeatable methodology, so two developers evaluating the same library can reasonably disagree with no way to reconcile why.

TechScope centralizes the objective, collectible signals into one deterministic score and shows the work behind it, so the answer is reproducible and auditable rather than a matter of opinion.

## 4. Goals

Goals are written as outcomes an engineering team can verify against `SCORING.md` and this document, not aspirations.

| # | Goal | How it's verified |
|---|---|---|
| G1 | A developer can retrieve a Health Score for any npm or PyPI package that resolves to a GitHub repository. | Search → resolve → score round-trip works end to end for benchmark-set packages and for at least one package outside the benchmark set. |
| G2 | The score is fully reproducible from disclosed inputs. | Given the same six raw metric inputs, the formula in `SCORING.md` §8 produces the same score, independently recomputable by an engineer from the displayed breakdown. |
| G3 | AI never influences the score. | The explanation service has no write path to the score storage; this is enforced architecturally, not by prompt instruction (`SCORING.md` §11.4). |
| G4 | Missing or low-confidence data is disclosed, never hidden or silently zero-filled. | Every score response includes a completeness indicator; `provisional`, `lower_confidence`, and `insufficient_data` states render distinctly in the UI. |
| G5 | The scoring model's credibility is empirically demonstrated, not asserted. | A validation report exists showing Spearman's ρ between computed scores and hand-assigned tiers, before and after weight recalibration (`SCORING.md` §10). |
| G6 | The product ships as the smallest surface that satisfies G1–G5. | No feature exists in V1 that isn't directly required to compute, display, or explain a score. |

## 5. Non-Goals

The following are explicitly excluded from V1. Their absence is a deliberate scope decision, not an oversight, and none of them should be re-introduced as a "small addition" during implementation.

- Authentication, user accounts, or GitHub OAuth.
- Personalized recommendations of any kind.
- Resume analysis or career coaching.
- Job market analysis.
- Repository analysis as a standalone product surface (e.g., a general-purpose "review my repo" tool). Note: fetching repo data to *compute the Health Score* is in scope; presenting repo-level code review, quality analysis, or advice unrelated to the six defined metrics is not.
- A browser extension.
- Notifications or alerts of any kind.
- Watchlists or saved packages (both require accounts, which are out of scope).
- Continuous, open-ended internet-wide scraping (V1 operates against a curated benchmark set plus on-demand lookups; see Section 9).
- Social features (comments, sharing feeds, voting, discussion).
- A chat interface for the AI layer. The AI produces one static explanation per score; it does not take follow-up questions or free-form prompts in V1.
- Side-by-side comparison of two or more packages. Each package's score is independently correct and displayable; a dedicated comparison UI is additional surface not required to answer the single-package question this MVP targets (see Section 19).
- Any qualitative score label or "grade" (e.g., "Healthy" / "At Risk") mapped from the numeric score. `SCORING.md` §10.1's four tiers (Thriving/Stable/Declining/Abandoned) exist to build and validate the benchmark set — they are not a validated score-to-label mapping, and inventing one for the UI would be adding a feature the methodology doesn't support.
- Any registry other than npm and PyPI, or any source host other than GitHub (`SCORING.md` §2).
- Any additional metric, or any change to metric weights, formulas, or thresholds beyond what `SCORING.md` defines.

## 6. Target Audience

Individual software developers and small-to-mid-sized engineering teams evaluating a specific programming language, framework, library, or tool before adopting or continuing to depend on it. The audience is technical: they can read a metric breakdown and a percentile without translation, so the product does not need to over-explain basic software engineering concepts.

## 7. Personas

**Priya — Backend Engineer, evaluating a dependency**
Priya is about to add a new library to a production service. She wants to know, in under a minute, whether the project is actively maintained and whether the maintenance burden falls on one person who could disappear. She reads the metric breakdown, not just the headline number.

**Marcus — Tech Lead, choosing a framework for a new project**
Marcus is deciding between two or three candidate frameworks for a project his team will own for years. He needs a defensible, non-subjective data point he can put in an architecture decision record — something more rigorous than "it has a lot of GitHub stars."

**Dana — Engineering Manager, auditing existing dependencies**
Dana periodically checks whether tools her team already depends on are showing early signs of decline (slowing commits, growing unresolved issues) before it becomes an incident. She looks up packages one at a time as part of a recurring but informal review, not through any saved list (V1 has no watchlists — she keeps her own external list).

## 8. User Stories

Grouped by the functional area they map to in Section 9.

**Search & resolution**
- As Priya, I want to search for a package by name so that I can find its Health Score without knowing its GitHub URL.
- As Priya, I want to be told clearly when a package can't be resolved to a GitHub repository, so I don't mistake silence for a good score.
- As Marcus, I want to disambiguate between an npm package and a PyPI package that share a name, so I score the one I actually mean to adopt.

**Score display**
- As Marcus, I want to see the overall 0–100 Health Score immediately, so I can form a first impression before reading details.
- As Priya, I want to see each of the six metrics and its individual contribution, so I understand *why* the score is what it is, not just what it is.
- As Dana, I want to see when a metric is unavailable rather than assumed zero, so I don't penalize a package for a data gap that isn't its fault.
- As Priya, I want to see a completeness indicator (e.g., 5 of 6 metrics available), so I can judge how much to trust the score.
- As Marcus, I want a brand-new package (under 90 days old) to be visibly marked provisional, so I don't treat a thin data history as a mature track record.
- As Priya, I want the Download Momentum metric to disclose when it may be inflated by non-human traffic, so I can weigh it accordingly.

**AI explanation**
- As Dana, I want a short plain-English explanation of the score, so I don't have to personally interpret six raw numbers under time pressure.
- As Marcus, I want the explanation to be generated strictly from the computed score and metrics, so I can trust it isn't the AI's own opinion of the package.

## 9. Functional Requirements

Requirements are grouped by feature area. Each is written to be testable. "MUST" indicates a hard requirement; "SHOULD" indicates a strong default that engineering may deviate from with documented reason.

### 9.1 Package Search & Resolution

- **FR-1.** The system MUST provide a search input accepting a free-text package name.
- **FR-2.** The system MUST allow the user to specify or disambiguate the registry (npm or PyPI) when a name exists in both, either via an explicit selector or a disambiguation prompt when a name matches on both registries.
- **FR-3.** On search, the system MUST attempt to resolve the package to a single GitHub repository using registry metadata (e.g., the `repository` field from the npm registry, or project URL metadata from PyPI).
- **FR-4.** If resolution fails, the system MUST return and display the exact state defined in `SCORING.md` §2: `{"score": null, "reason": "unsupported_or_unresolved"}`. The UI MUST render this as an explicit "not supported" state, not as an error or a blank/zero score.
- **FR-5.** Resolution and scoring MUST work for any resolvable npm/PyPI package, not only the curated benchmark set. Packages outside the benchmark set are ranked against the benchmark set as a fixed external reference population, per `SCORING.md` §6.

### 9.2 Score Computation & Storage

- **FR-6.** The system MUST compute the six metrics exactly as defined in `SCORING.md` §5.1–5.6, using only the data sources listed in `SCORING.md` §4.
- **FR-7.** The system MUST compute percentile rank for each available metric against the curated benchmark set, per `SCORING.md` §6, and combine them using the weighted-average formula in `SCORING.md` §8.
- **FR-8.** The system MUST NOT zero-fill an unavailable metric. Unavailable metrics MUST be excluded from both the numerator and denominator of the weighted average, consistent with `SCORING.md` §8–9.
- **FR-9.** If fewer than 4 of 6 metrics are available for a package, the system MUST return `{"score": null, "reason": "insufficient_data"}` and MUST NOT display a numeric score.
- **FR-10.** If the resolved repository's `created_at` date is less than 90 days before the scoring run, the response MUST include `"provisional": true`.
- **FR-11.** The Download Momentum metric response MUST include a `lower_confidence` flag per the disclosed weakness in `SCORING.md` §5.5 (CI/mirror traffic inflation, no installer-type filter available).
- **FR-12.** Every score response MUST include `"methodology_version": "1.0"` and a completeness object in the shape `{"health_score": <int>, "metrics_available": <int>, "metrics_total": 6}`.
- **FR-13.** Computed scores and their full metric breakdown MUST be persisted to storage before any explanation is generated (see 9.4). Score computation and score explanation MUST remain physically separate pipeline stages, per `SCORING.md` §11.4.

### 9.3 Refresh & Data Collection

- **FR-14.** All metrics for all benchmark-set packages MUST refresh on a single weekly batch job. No per-metric refresh schedule (differentiated TTLs) is in scope for V1 (`SCORING.md` §11.1).
- **FR-15.** For a non-benchmark package looked up for the first time, the system MUST compute and cache its score on demand; the cached result SHOULD be treated as stale and eligible for recomputation on the same weekly cadence as the benchmark set, for consistency of freshness across the product.
- **FR-16.** A `202 Accepted` (empty body) response from GitHub's `/stats/contributors` endpoint MUST be treated as "retry after backoff," and MUST NOT be interpreted as zero commits, per `SCORING.md` §11.2.
- **FR-17.** All GitHub REST calls MUST use an authenticated token and MUST stay within the 5,000 requests/hour budget described in `SCORING.md` §11.3. No GraphQL batching is in scope for V1.
- **FR-18.** npm and PyPI download data MUST be collected via the unauthenticated `api.npmjs.org` and `pypistats.org` endpoints respectively, per `SCORING.md` §4. No third-party data broker (e.g., Libraries.io, npms.io) and no BigQuery dependency is permitted in V1.

### 9.4 AI Explanation Layer

- **FR-19.** The explanation service MUST be a separate, stateless call that reads only the already-persisted `{health_score, metrics, completeness}` object. It MUST NOT have any code path capable of writing to score storage, and MUST NOT receive raw, pre-normalization API data.
- **FR-20.** The generated explanation MUST reference only the metrics and values present in the persisted object. It MUST NOT introduce claims, opinions, or external knowledge about the package not derivable from that object.
- **FR-21.** When a metric carries a disclosed methodological caveat relevant to the package's result (e.g., `lower_confidence` on Download Momentum, or a high Contributor Concentration value on an otherwise strong small package), the explanation SHOULD surface that caveat in context, consistent with `SCORING.md` §5.4's stated mitigation ("mitigated by disclosure and by the AI explanation layer surfacing it in context").
- **FR-22.** The explanation is a single static block of generated text per score. V1 MUST NOT expose a chat interface, follow-up prompt field, or any free-form user input to the LLM.
- **FR-23.** If explanation generation fails, the score and metric breakdown MUST still render normally; the explanation is an enhancement layer, not a blocking dependency of the score itself.

### 9.5 Score & Metric Display

- **FR-24.** The package detail view MUST display: the numeric Health Score (0–100) or the appropriate null-state per FR-4/FR-9; each of the six metrics with its weight, its percentile score (or "unavailable"), and a one-line plain-language definition; the completeness indicator; the `provisional` and `lower_confidence` flags when present; the `methodology_version`; and the AI explanation.
- **FR-25.** The UI MUST distinguish, visually and textually, between three null/degraded states: `unsupported_or_unresolved`, `insufficient_data`, and a complete score with `provisional: true`. These are not interchangeable and MUST NOT share the same visual treatment.
- **FR-26.** The UI MUST NOT display any score-to-label mapping (e.g., "Healthy," "At Risk") that is not defined in `SCORING.md`.

### 9.6 Internal / Operational Requirements (not user-facing)

- **FR-27.** The system MUST provide internal tooling (may be a simple structured file or admin script; does not require a public UI) to curate and maintain the 50–100 package benchmark set, including: package identity, assigned tier (Thriving/Stable/Declining/Abandoned), and a written justification per package, per `SCORING.md` §10.1.
- **FR-28.** The system MUST support running the validation procedure in `SCORING.md` §10.2–10.6: computing scores for the full benchmark set, calculating Spearman's rank correlation between computed score and assigned tier, identifying the specific metric(s) responsible for any mismatch, and recording manual weight adjustments with a written justification tied to a specific finding.
- **FR-29.** Every weight change resulting from FR-28 MUST be logged with the prior value, new value, and the specific benchmark mismatch that motivated it.

## 10. Non-Functional Requirements

| Category | Requirement |
|---|---|
| Performance — cached score | A benchmark-set package's score, already computed by the weekly batch, MUST be retrievable in under 500ms (server-side, excluding client network). |
| Performance — first-time lookup | A non-benchmark package looked up for the first time MUST complete the full resolve-and-compute path (GitHub + npm/PyPI calls) in under 15 seconds, with the UI showing a loading state throughout. |
| Reliability | The weekly batch job MUST complete for at least 99% of benchmark-set packages per run; failures for individual packages MUST be logged and retried, not allowed to silently fail the whole batch. |
| Rate-limit safety | Total GitHub REST usage MUST stay within the 5,000 requests/hour authenticated budget at benchmark scale (~100 packages × ~4 calls), with headroom for on-demand non-benchmark lookups. |
| Data integrity | No metric is ever zero-filled for unavailable data (this is a hard invariant, not a default — see FR-8). |
| Transparency | Every score response is traceable to a `methodology_version`; every weight change is traceable to a logged justification (FR-29). |
| Security | The GitHub API token MUST be held server-side only and MUST NOT be exposed to the client. No PII is collected, since V1 has no accounts. |
| Availability | The read path (score + explanation retrieval) SHOULD target 99.5% uptime, independent of whether the weekly batch job is currently running. |
| Observability | Every score request MUST be logged with `methodology_version`, completeness, and any degraded-state flags (`provisional`, `lower_confidence`, `insufficient_data`, `unsupported_or_unresolved`) for auditability. |
| Accessibility | The UI MUST meet WCAG 2.1 AA for the search flow and package detail view. |
| Browser support | Current stable versions of evergreen browsers (Chrome, Firefox, Safari, Edge). No legacy browser support required. |

## 11. Product Scope

**In scope for V1:**
- Search for an npm or PyPI package by name, with registry disambiguation.
- Resolution of a package to a GitHub repository.
- Computation and display of the six-metric Health Score exactly per `SCORING.md`.
- Display of per-metric breakdown, weights, and percentile scores.
- Completeness indicator and all defined degraded/null states (`provisional`, `lower_confidence`, `insufficient_data`, `unsupported_or_unresolved`).
- A single, static, non-interactive AI-generated explanation of the computed score.
- Weekly batch refresh of the benchmark set; on-demand compute-and-cache for other resolvable packages.
- Internal benchmark curation and validation tooling (Spearman's ρ, mismatch analysis, logged weight recalibration).

**Explicitly out of scope for V1** (restated from Section 5 and enforced here as scope, not aspiration):
Authentication, user accounts, GitHub OAuth, personalized recommendations, resume analysis, career coaching, job market analysis, general repository analysis, browser extension, notifications, watchlists, continuous internet-wide scraping, social features, side-by-side comparison, a chat/conversational AI interface, any qualitative score label not defined by the methodology, any registry beyond npm/PyPI, any source host beyond GitHub, and any metric, weight, or formula not defined in `SCORING.md`.

## 12. Information Architecture

```
Home / Search
 └─ Search input (package name + registry disambiguation when needed)
     └─ Package Detail View
         ├─ Score Summary
         │    ├─ Numeric Health Score (0–100) OR null-state message
         │    ├─ Completeness indicator (e.g., "5 of 6 metrics available")
         │    ├─ State flags: provisional / lower_confidence (contextual, per metric)
         │    └─ methodology_version + last-refreshed timestamp
         ├─ Metric Breakdown (6 rows)
         │    └─ Per metric: name, one-line definition, weight, percentile score or "unavailable"
         ├─ AI Explanation
         │    └─ Static generated paragraph, sourced only from the Score Summary + Metric Breakdown data
         └─ Null / Degraded States (mutually distinct rendering)
              ├─ unsupported_or_unresolved
              ├─ insufficient_data
              └─ provisional (renders alongside a complete score, not instead of it)
```

There is no account area, no settings page, no dashboard, and no navigation beyond search → detail view. This is the entire product surface.

## 13. User Flows

**Flow 1 — Successful lookup, complete data**
User enters a package name → registry auto-detected or disambiguated → resolves to a GitHub repo → all 6 metrics available → score computed and persisted → explanation generated from persisted object → detail view renders score, breakdown, and explanation.

**Flow 2 — Unresolved package**
User enters a package name → no matching GitHub repository can be determined from registry metadata → system returns `unsupported_or_unresolved` → detail view renders an explicit "not supported" state with no score, no breakdown, no explanation attempt.

**Flow 3 — Insufficient data**
User enters a package name → resolves successfully → fewer than 4 of 6 metrics can be collected (e.g., GitHub data available but download stats unavailable) → system returns `insufficient_data` → detail view shows which metrics *were* collected (for transparency) but explicitly withholds a numeric score.

**Flow 4 — New package (provisional)**
User enters a package name → resolves successfully, ≥4 metrics available, repo created less than 90 days ago → score computes normally but response includes `provisional: true` → detail view renders the score with a persistent, clearly labeled provisional notice, and the explanation text acknowledges the limited track record.

**Flow 5 — Ambiguous registry**
User enters a name that exists on both npm and PyPI → system prompts the user to pick a registry before proceeding → flow continues as Flow 1–4 depending on outcome.

| Metric | What it validates |
|---|---|
| % of searches that resolve to a GitHub repo and produce either a score or a well-defined null-state (not an unhandled error) | Search/resolution robustness (G1) |

## 15. Risks and Assumptions

**Risks**

- **GitHub API rate limiting under real usage.** The 5,000/hour budget comfortably covers benchmark-scale batch refresh (`SCORING.md` §11.3), but on-demand lookups of non-benchmark packages add variable load. Mitigation: cache on-demand results and refresh on the same weekly cadence rather than per-request.
- **Download Momentum inflation.** npm/PyPI download counts include CI and mirror traffic with no installer-type filter available; this is disclosed via `lower_confidence`, not solved, in V1 (`SCORING.md` §5.5).
- **Contributor Concentration penalizes small, expert-maintained packages.** This is a known, disclosed weakness (`SCORING.md` §5.4) that V1 mitigates only through disclosure and AI-surfaced context, not through archetype-aware weighting (that's v2, Section 19).
- **Benchmark set size and curation quality.** A 50–100 package set is small enough that curation errors (mis-tiered packages) could meaningfully skew validation results; `SCORING.md` §10.1 requires written justification per package specifically to reduce this risk, but it isn't eliminated.
- **LLM explanation drift.** Despite architectural separation from scoring, an LLM could still introduce unsupported claims or editorializing beyond the given data. Mitigation: tightly scoped prompting constrained to the persisted score/metrics object only (FR-19–FR-21), and no user-facing follow-up prompt surface that could expand the model's effective scope.
- **Package name collisions across npm and PyPI.** Ambiguous names require explicit disambiguation (FR-2); failure to disambiguate correctly could return a score for the wrong package.
- **Cold-start reliability for very new packages.** The 90-day provisional threshold is a single date check, not a confidence model; a package at 91 days old is treated identically to one at 5 years old for weighting purposes, which is a known simplification, not a bug to fix in V1.

**Assumptions**

- Registry metadata (npm `repository` field, PyPI project URLs) is populated accurately enough by package maintainers to make automated GitHub resolution viable for the large majority of well-known packages.
- The benchmark set, once curated, is stable enough week-to-week that weekly (not real-time) refresh is an acceptable trade-off — consistent with `SCORING.md` §11.1's explicit rejection of differentiated TTLs for V1.
- GitHub, npm registry, and pypistats.org API terms of service permit this usage pattern at the described volume.

## 18. Version 1 Acceptance Criteria

V1 is ready to ship when all of the following are true:

1. The score formula in `SCORING.md` §8 is implemented exactly; unit tests reproduce hand-calculated expected scores for a sample of benchmark packages.
2. No metric is ever zero-filled; unavailable metrics are excluded from both numerator and denominator of the weighted average.
3. A package with fewer than 4/6 metrics available returns exactly `{"score": null, "reason": "insufficient_data"}` and the UI withholds a numeric score.
4. A package that cannot be resolved to a GitHub repo returns exactly `{"score": null, "reason": "unsupported_or_unresolved"}`.
5. A repository younger than 90 days returns `"provisional": true` alongside its score.
6. Every score response includes `"methodology_version": "1.0"` and a completeness object (`health_score`, `metrics_available`, `metrics_total`).
7. Download Momentum responses include the `lower_confidence` flag per §5.5.
8. The AI explanation service reads only persisted `{health_score, metrics, completeness}` data, has no write path to score storage, and this separation is verifiable in the codebase (not just documented).
9. A benchmark set of 50–100 packages exists, spans all four tiers (Thriving/Stable/Declining/Abandoned), and each package has a written tier justification cross-checked against GitHub `archived` status, deprecation notices, or last-commit recency.
10. Spearman's ρ between computed scores and assigned tiers has been calculated, at least one recalibration cycle has been run with logged, justified weight changes, and ρ has been recalculated post-recalibration with the before/after delta documented.
11. The weekly batch job successfully refreshes the full benchmark set and is observable/loggable per run.
12. `202 Accepted` responses from `/stats/contributors` trigger retry-with-backoff and are never treated as zero commits.
13. GitHub API usage stays within the 5,000 requests/hour authenticated budget under expected benchmark-scale plus on-demand load.
14. The shipped product contains no authentication, accounts, OAuth, personalization, watchlists, notifications, browser extension, comparison view, chat interface, or social features.
15. The UI does not display any score-to-label mapping not defined in `SCORING.md`.
16. All four defined degraded/null states (`unsupported_or_unresolved`, `insufficient_data`, `provisional`, `lower_confidence`) render with visually and textually distinct treatment in the package detail view.

## 19. Future Work

Listed here because it is explicitly out of V1, not because it is unimportant. Items below are pulled directly from `SCORING.md` §12 (methodology roadmap) and from this PRD's Non-Goals (product roadmap); nothing here should be pulled forward into V1 without a new PRD revision.

**Methodology roadmap (from `SCORING.md` §12):**
- Archetype classification and archetype-specific weighting, once the corpus is large enough per archetype.
- Cohort-based percentile normalization (per registry + archetype), the natural successor to the current global percentile approach.
- Full Bus Factor (smallest-N contributors for ≥50% of commits), upgrading from the current single-ratio Contributor Concentration proxy.
- Ecosystem Dependents Ratio, requiring a fourth data source (e.g., Libraries.io or npms.io) outside the current GitHub/npm/PyPI boundary.
- Bot-aware stale-issue-closure filtering for Issue Resolution Health, requiring per-issue event/label inspection.
- Release Cadence Variance (coefficient of variation), reintroduced once benchmark packages have enough release history for the statistic to be meaningful.
